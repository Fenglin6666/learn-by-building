# learn-by-building

> 不是让 AI 写得更快，是让 AI 写得更少。

一个给 AI 编码助手用的**学习协议**。它把「AI 写完整个项目、你负责点头」，改成「AI 搭脚手架、你写业务代码、AI 审你的代码」。

---

## 它治什么病

写下这个协议的人的原话：

> 现在 LLM 直接生成代码确实方便，但当我有一个点子、把它描述给 AI 来完成，往往效果不好。代码很多，我自己想改根本无从下手。最关键的是，我在整个过程中学到的东西寥寥无几，最多是一些概念。
>
> 本质上我只是把项目外包给了 AI——这更像是一种雇主关系，而不是伙伴关系。

对照一下你是不是也这样：

- [ ] 点子丢给 AI，出来的东西不太对，但也说不上哪里不对
- [ ] 代码能跑，但我不敢动，一动就崩
- [ ] 项目做完了，我能讲出几个名词，但讲不出它为什么这么组织
- [ ] 下次遇到类似需求，我还是从零开始问 AI

如果是，这个协议是给你写的。

---

## 一条铁律

**键盘在用户手上。**

AI 写业务代码的唯一合法理由是「这块你现在写不了」，且必须标注为黑箱，并附上「你以后要懂的三件事」。

一旦 AI 开始成段写业务逻辑，这个协议就失效了——它会退化成普通的「AI 代写」，你又一次变回旁观者。

---

## 核心机制：密度四档

同一个模块，AI 可以按四种密度交给你。密度**自动递减**，这就是脚手架渐撤。

| 档位 | AI 给什么 | 你写什么 |
|------|-----------|----------|
| **L3 手把手** | 签名 + 职责 + 输入输出 + 边界条件 + **编号实现步骤** + 手算样例 | 照步骤填 |
| **L2 给框架** | 去掉实现步骤，其余照给 | 自己想步骤 |
| **L1 给签名** | 只给签名 + 一句话职责 | 自己想输入输出和边界 |
| **L0 给问题** | 只给「这个文件解决什么问题」，文件是空的 | 从零设计 |

规则：起步 L3，**每完成 2 个模块降一档**。用户说「太难了」就升回去。

一直停在 L3，你永远在翻译别人的步骤；直接跳到 L0，第一步就死。中间这条斜坡才是学到东西的地方。

## 交接产物是代码文件，不是文档

AI 不给你一份 markdown 规格让你读，而是直接在代码文件里留骨架和 TODO：

```python
# data_loader.py
# 职责：把 data.csv 读成 [{name, amount}] 形式的列表。
# 上层谁在用：stats.py 的 compute_average()

def load_rows(path):
    """读 CSV，返回字典列表。空文件返回 []，缺列抛 ValueError。"""
    # 手算样例：文件内容是 "name,amount\n苹果,10" 时，返回 [{'name': '苹果', 'amount': 10}]
    # TODO 1: 打开文件（注意编码，中文可能不是 utf-8）
    # TODO 2: 读表头，校验 name / amount 两列都在，缺了就抛 ValueError
    #   ⚠️ 黑箱：这里用 csv.DictReader 而不是手动 split(',')，原因你写完要回来问
    # TODO 3: 逐行转成字典，amount 转成数字
    # TODO 4: 返回列表
    pass
```

这样任何语言都成立——注释是唯一跨语言的通用语。

## 和其他「教学模式」的区别

| | 谁写代码 | 谁讲解 |
|---|---|---|
| 普通的 teach-mode 类技能 | AI | AI |
| **本协议** | **你** | AI（只在 review 和黑箱时） |

判据很简单：**如果一次会话结束时你一行代码都没写，那就是 teach-mode 在跑，不是这个协议。**

用户明确说「今天只想看懂，不想写」时，应该切回 teach-mode，别硬撑。

## 使用

第一次开一个项目，直接说：

> 我想做一个记账工具，用这个方式。

它会问你三件事（做什么、什么技术栈、打算做多久），然后建目录、装依赖、给出模块表，把第一块交给你。

之后每次开工它会读 `.learn/state.md` 恢复进度——你的水平、模块清单、当前密度、反复犯的错，都记在里面。

**快捷口令**：`太难了` / `太简单了` / `我卡住了` / `直接做完` / `帮我改` / `讲一下这块`

## 设计依据

`docs/evidence.md` 里有完整证据清单（含 DOI 和链接，分「强 / 中 / 弱 / 个案」四级）。

最硬的五条：

1. **验收只看「撤掉 AI 之后」**。练习期表现与学习结果可以背离——有个近千人的 RCT 里，练习期用 AI 提升 48%~127%，撤掉 AI 后反而比从没用过 AI 的对照组低 17%。
2. **同一个模型，护栏决定方向**。不给答案 + 逐步引导，能把 −17% 扭成不掉（哈佛物理 194 人交叉 RCT，效应 0.63–1.3 SD，还更省时间）。
3. **新手先给完整范例，然后撤**。范例 → 补全 → 独立，跳过「补全」这档会掉效果。这就是密度四档的依据。
4. **先让他卡住，卡完必须讲**。166 项比较的元分析，先解题后讲解 g=0.36；前提是失败之后必须有明确讲解。
5. **别拿「任务完成」当学会**。AI 组没更快却学得更少——效率类指标在这件事上系统性说谎。

## 已知局限

诚实写在前面，别指望它解决所有问题：

- **没经过真实项目验证。** 这是从证据和一次深度设计访谈里推出来的协议，不是跑过十个项目打磨出来的。
- **砍掉了验收。** 协议只做代码审查，不做「撤掉 AI 重写」这类检验。代价是：你没法区分「我写完了」和「我学会了」。这是权衡，不是疏忽。
- **不练「改别人代码」的能力。** 协议只练「从规格写出代码」。而维护能力（读懂并改动 AI 写的代码）是另一个技能，目前没覆盖。黑箱清单里留了软出口，但没强制。
- **两个证据空洞。** 「新手+专家配对时谁打字学得更多」和「review AI 代码的学习收益」，都没有对照实验。协议里涉及这两处的地方是假设，不是研究支持。
- **需要你愿意慢下来。** L3 那一档要你手写几十行，第一次你大概率会想「算了让 AI 写完吧」。到那一步，说「太难了」，那是密度该降的信号。
